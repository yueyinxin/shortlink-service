# ADR-0001: 采用按功能垂直切分 + 域内分层的代码组织方式

- **状态**：已接受
- **日期**：2026-09-24
- **相关**：架构设计 §4

## 背景

需要确定代码的包组织方式。Java 项目有两条主流路线：

1. **按技术分层**：顶层包为 `controller` / `service` / `repository` / `entity`。
2. **按功能垂直切分**：顶层包为 `auth` / `link` / `stats`，每个功能域**内部**再分层。

国内多数 Spring Boot 项目采用第 1 种。本项目功能域边界清晰（认证、短链、统计三者几乎无交叉逻辑），需要判断是否沿用惯例。

## 决策

采用 **按功能垂直切分 + 域内分层**：

```
link/
├── LinkController.java      ← web 层
├── LinkService.java         ← application 层
├── ShortLink.java           ← domain 层
├── ShortCodeGenerator.java  ← domain 层
└── infrastructure/
    ├── JpaShortLinkRepository.java
    └── RedisLinkCache.java
```

每个功能域内部仍严格遵守 `web → application → domain ← infrastructure` 的依赖方向。

## 理由

**决定性因素是「改动的影响半径」**。以"给短链增加一个过期提醒功能"为例：

| | 按技术分层 | 按功能垂直切分 |
| --- | --- | --- |
| 需要触碰的顶层目录 | 4 个（controller/service/repository/entity） | 1 个（link/） |
| 改动的代码在目录中的位置 | 分散在 4 处，每处都混着无关功能 | 集中，同目录下都是相关代码 |
| 未来拆分微服务 | 需跨 4 个包大范围搬迁，易漏 | 整个目录搬走即可 |

其次，垂直切分天然约束了**跨功能域的耦合**。在 `link` 包内无法直接 import `stats` 的内部类（需要显式跨越包边界），这种"摩擦"会促使开发者思考依赖是否合理。而在按技术分层的结构里，`LinkService` 调用 `StatsService` 看起来完全正常，耦合会在不知不觉中累积。

## 后果

### 正面

- 功能改动集中在一个目录，影响半径可控。
- 功能域边界显式化，未来拆分服务的成本最低。
- 新成员接手某个功能时，只需理解一个目录。

### 负面（接受的代价）

- 对完全不了解本项目的开发者，"先去哪个包找 Controller" 需要先看一眼结构。缓解措施：包名与功能名严格对应（`link` 域对应短链功能），且在架构文档中提供了完整的目录树。
- 每个功能域内都要重复一套 `web/application/domain` 的子结构，有少量样板感。本项目功能域只有 3 个，可接受。

## 替代方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 纯按技术分层 | 改动影响半径大，跨功能耦合难以察觉；不利于未来拆服务 |
| 严格六边形架构（`port` / `adapter` 显式包） | 对当前规模是过度设计。本项目用"域内分层"已获得大部分收益，同时保持目录结构易于浏览 |
| 单模块内不再分层（Controller 直接调 Repository） | 核心业务逻辑（短码生成、跳转判定）将无法脱离 Spring 容器做单元测试，测试会变慢且脆弱 |
