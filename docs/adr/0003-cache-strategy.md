# ADR-0003: 短链缓存采用 Cache-Aside 模式，并同时处理穿透与雪崩

- **状态**：已接受
- **日期**：2026-09-24
- **相关**：US-05, AC-05.5, AC-05.6

## 背景

跳转占总流量的 99% 以上，且同一个热门短链会被反复访问。若每次跳转都查 MySQL，在 1000 QPS 下数据库将承受全部压力，且 P99 延迟无法达到 50 ms 的目标。

引入 Redis 缓存是明确的选择。需要决策的是三个具体问题：

1. 缓存什么粒度？
2. 一致性如何维护？
3. 缓存穿透（查询不存在的短码）和缓存雪崩（大量 key 同时失效）如何防御？

## 决策

### 1. 缓存整个短链对象，而非只缓存 URL 字符串

```json
{
  "id": 12345,
  "originalUrl": "https://example.com/very/long/path",
  "status": "ACTIVE",
  "expiresAt": "2026-12-31T23:59:59",
  "userId": 42
}
```

### 2. 一致性采用 Cache-Aside（旁路缓存）

- **读**：先查缓存，未命中查数据库，然后写回缓存。
- **写**：**先更新数据库，再删除缓存**（不是更新缓存）。

### 3. 穿透防御：空值缓存

查询数据库不存在的短码，也写入缓存，值为特殊标记 `__NULL__`，TTL 60 秒。

### 4. 雪崩防御：TTL 加随机抖动

正常缓存 TTL 为 `24 小时 ± 10%` 随机值（即 21.6h ~ 26.4h）。

### 5. 降级：缓存故障时直查数据库

Redis 异常被捕获并记录日志，降级为直接查询数据库，**跳转仍然可用**（AC-05.6）。

## 理由

### 关于缓存粒度

只缓存 URL 字符串会导致一个隐蔽的 bug：跳转前需要判断短链是否已过期/被禁用，而这两个字段不在缓存里，就必须回查数据库——**缓存命中却仍要访问数据库，缓存就失去了意义**。

缓存整个对象后，命中缓存即可完成全部状态判定，热路径零数据库访问。

### 关于「先更新 DB 再删缓存」而非「先删缓存再更新 DB」

两种顺序在并发下都不完美，但失败概率差一个数量级：

**先删缓存，再更新数据库**的问题：

```
时刻  T1: 线程A 删除缓存
      T2: 线程B 读缓存未命中 → 读DB（读到旧值）
      T3: 线程A 更新数据库（新值）
      T4: 线程B 把旧值写回缓存     ← 缓存里长期是旧值
```

**先更新数据库，再删缓存**：出现不一致需要「读请求恰好在更新DB之后、删缓存之前完成读DB和写缓存」，这个窗口极窄（删缓存是紧接着的动作），且下一次读就会修复。

**更关键的是：删除缓存比更新缓存更不容易出错**。更新缓存需要把新状态完整计算一遍；而删除缓存只是让下次读去数据库取，是幂等的、无条件正确的操作。

### 关于为什么不用「延迟双删」

「先删缓存 → 更新DB → 延迟 500ms 再删一次」能进一步压低不一致窗口，但它引入了两个新问题：延迟时间无法科学确定（500ms 是拍脑袋的）；以及引入一次额外的、几乎总是无用的删除操作。

本场景的缓存是**只读为主、极少更新**的状态（用户很少修改已创建的短链）。不一致窗口最长只有「更新DB到删缓存」的几毫秒，且下一次访问即自动修复（Cache-Aside 的读路径会写回新值）。为此引入延迟双删的复杂度不划算。已记录在架构风险表中。

### 关于空值缓存 TTL 取 60 秒

比正常缓存短得多，原因是空值缓存本身是一个权衡：

- TTL 太长：用户刚创建的短码若在这期间首次被访问，会命中空值缓存导致 404 ——「刚创建的链接打不开」，用户体验很差。
- TTL 太短：失去防穿透的意义。

60 秒是一个折中。同时，**创建短链时会主动清理该短码的空值缓存**（虽然创建前该码不应存在，但自定义短码可能被用户反复尝试），彻底消除了上述冲突。

### 关于雪崩抖动

如果 10 万个短链在同一时刻批量导入，它们的 24 小时 TTL 会在同一秒集中到期，届时全部请求穿透到数据库。这就是缓存雪崩。±10% 抖动把到期时间摊开到约 4.8 小时窗口内。

### 关于不引入布隆过滤器

布隆过滤器是防穿透的强手段，但：

- 需要维护一个与数据库同步的位图，短链删除后无法从布隆过滤器移除条目（需重建或引入计数布隆过滤器）。
- 已用空值缓存 + 限流（AC-08.1 限制单 IP 300 次/分钟）覆盖了穿透攻击的主要场景——攻击者无法以高速率扫描不存在的短码。

在压测证明空值缓存不足以防护之前，不引入。这是有意的"先不做"，已记录在范围的"范围外"表中。

## 后果

### 正面

- 热路径（缓存命中）零数据库访问，P99 延迟由 Redis 网络往返决定。
- Redis 完全故障时跳转仍可用，可用性提升（AC-05.6）。
- 穿透、雪崩两个经典问题均有对应措施，且有明确参数。

### 负面（接受的代价）

- 缓存与数据库存在最长数毫秒的不一致窗口。本场景可接受，因为短链一旦创建几乎不再修改。
- 每个不存在的短码查询会占用 60 秒的 Redis 内存。在恶意扫描下会消耗内存，缓解措施是限流。
- 缓存对象比纯 URL 字符串大（约 200 字节 vs 30 字节）。相对 Redis 的容量和 24 小时 TTL，成本可忽略。

## 替代方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 只缓存 URL 字符串 | 状态判定仍需查库，缓存失效 |
| 更新 DB 后**更新**缓存（而非删除） | 并发下易写入过期数据；更新逻辑需与读路径保持一致，易出错 |
| 延迟双删 | 延迟时间无法科学确定；本场景更新极少，收益不抵复杂度 |
| 布隆过滤器防穿透 | 条目无法删除，需重建；当前空值缓存 + 限流已足够 |
| 缓存永不过期 + 主动刷新 | 内存不可控，且需要额外的刷新调度器 |
| 不用缓存，直接查 MySQL | 无法达到 1000 QPS / P99 50ms 的目标 |
