# ADR-0004: 统计采用「Redis 实时计数 + 定时刷库」，UV 用 HyperLogLog，查询时合并增量

- **状态**：已接受
- **日期**：2026-09-24
- **相关**：US-07, AC-05.5, AC-07.1, AC-07.3

## 背景

需要在跳转时记录访问数据（PV / UV），但存在一个根本矛盾：

- **跳转必须极快**（P99 < 50 ms），任何同步写操作都会拖慢它。
- **统计必须能看到最新数据**，用户刚发的链接点了几下，刷新后台应该立刻看到。

如果只在内存里攒着，重启就丢；如果每个请求都同步写 MySQL，跳转就慢了。

## 决策

### 1. 跳转路径：只写 Redis，一次 pipeline

```java
// 一次往返完成两条命令
redisTemplate.executePipelined(connection -> {
    connection.stringCommands().incr(pvKey(code, date));
    connection.hyperLogLogCommands().pfAdd(uvKey(code, date), clientIp);
    return null;
});
```

### 2. 定时刷库：每分钟一次

`@Scheduled(fixedDelay = 60s)` 扫描**当日**与**前一日**的计数 key，UPSERT 进 MySQL，成功后删除 Redis 中已落库的计数。

刷库使用 MySQL 的 `INSERT ... ON DUPLICATE KEY UPDATE pv = pv + VALUES(pv)` 语义，保证幂等（重复刷库不会导致 PV 翻倍）。

### 3. 查询路径：合并 Redis 增量（读时修复）

```
展示给用户的 PV = MySQL 已落库的 PV + Redis 中尚未落库的当日增量
```

对于当日数据，`StatsService` 总是把 Redis 的当前计数加到数据库值上。

### 4. UV 使用 Redis HyperLogLog（`PFADD` / `PFCOUNT`）

不用 Set，不用 `INCR` 计数不同 IP。

## 理由

### 为什么不用消息队列

这是本项目最重要的一条"有意的克制"。

MQ（Kafka / RocketMQ / RabbitMQ）是异步统计的标准方案，但它引入的成本很高：

- 多一个中间件要部署、监控、调优、处理故障。
- 需要处理消息丢失、重复消费、消费积压。
- 本地开发环境变成"必须同时起 4 个容器"。

而本场景的真实需求只是「延迟不超过 60 秒的最终一致」。Redis + 定时任务用**一个已经存在的组件**就满足了：

| | MQ 方案 | 本项目方案 |
| --- | --- | --- |
| 需要新增中间件 | 是 | 否（复用已有 Redis） |
| 本地开发依赖 | MySQL + Redis + MQ | MySQL + Redis |
| 数据丢失风险 | 需处理生产/消费两端 | 最多丢失 60 秒增量 |
| 峰值削峰能力 | 强 | 弱（但 Redis 写入已是微秒级） |

**取舍点**：如果未来需要「精确到每次访问的明细流水」（如风控审计），或统计写入量超过 Redis 单实例吞吐，则必须引入 MQ。当前需求（按天聚合的 PV/UV）不需要。

### 为什么 UV 用 HyperLogLog

UV 需要"去重计数"。朴素做法是存一个 Set 记录所有访问过的 IP，但内存占用与 IP 数量成正比：

| 独立 IP 数量 | Redis Set 内存 | HyperLogLog 内存 |
| --- | --- | --- |
| 1 万 | ≈ 640 KB | 12 KB |
| 100 万 | ≈ 64 MB | 12 KB |
| 1 亿 | ≈ 6.4 GB | 12 KB |

HyperLogLog 使用固定 12 KB 内存，标准误差 0.81%。对于"评估投放效果"这个业务场景，100 万 UV 有 ±8100 的误差完全不影响决策——运营需要知道的是"这次投放带来了 10 万还是 100 万访问"，不是"精确到个位数"。

**注意**：HyperLogLog 只支持 `PFADD` 和 `PFCOUNT`，**无法删除单个元素**，也无法列举成员。这是它换取内存效率的代价。本项目不需要这两个能力。

### 为什么查询时要合并 Redis 增量

如果查询只读 MySQL，会有最长 60 秒的"数据停滞"：用户点了 10 次链接，后台仍然显示旧数字。这种"看起来坏了"的体验会引发大量无效的客服/工单。

合并增量后，**读路径总是最新的**，而**写路径保持异步**。数据库在统计链路上退化为纯粹的持久化存储，不再是实时数据源。

实现上需要注意：MySQL 中不存在当日记录时（首次访问），增量就是全部 PV，不能因为"查不到记录"就返回 0。

### 关于刷库为什么要处理「前一日」

当日 23:59:59 之后，定时任务可能还没跑完最后一次刷库，日期已经跨天。此时前一日的数据残留在 Redis 中。若不处理，这部分访问会永久丢失。

因此刷库任务每次都同时处理**当日**和**前一日**两个日期，保证跨天边界的增量最终被落库。

### 关于刷库的幂等性

刷库成功后删除 Redis key。但如果删除失败（网络抖动），下次任务会再次读到相同的计数并重复累加。

**必须**让刷库操作幂等：使用 `pv = pv + VALUES(pv)`（增量累加）配合"先落库、后删除"的顺序，在删除失败时会导致重复累加——这是不幂等的。

真正的解法是**先原子地取出并清零**（`GETSET` 或 Lua 脚本 `INCRBY ... -n`），再落库。本项目采用 Lua 脚本实现「取值并重置」，脚本原子执行，保证同一份计数只会被取出一次。

## 后果

### 正面

- 跳转路径无任何 MySQL 写操作，响应时间与统计无关（满足 AC-05.5）。
- 查询始终返回最新数据（满足 AC-07.3）。
- UV 统计内存恒定，不随流量增长。
- 不引入 MQ，部署与本地开发保持简单（3 个容器：app + MySQL + Redis）。

### 负面（接受的代价）

- **最多丢失 60 秒统计**：若 Redis 崩溃且未持久化，这 60 秒的增量会丢失。对统计场景可接受（不是资金数据）。
- **单实例限制**：`@Scheduled` 在多实例部署下会重复执行。虽然 Lua 脚本的原子取出保证了同一份计数不会被重复累加（不会翻倍），但仍需在多实例前引入分布式锁。已记录在架构风险表。
- **HyperLogLog 有 0.81% 误差**：验收标准 AC-07.1 中明确写出了 ±1 的容差，而不是假装精确。
- **无法做明细查询**：本方案只保留按天的聚合值，无法回答"某次具体访问来自哪里"。若需要，属于范围外的新需求。

## 替代方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 每次跳转同步写 MySQL | 跳转路径引入数据库写，无法达到延迟目标 |
| MQ（Kafka/RocketMQ）异步消费 | 当前需求不需要峰值削峰与明细流水；引入的部署与运维成本远超收益 |
| Redis 计数 + 实时同步到 MySQL（定时 1 秒） | 刷库过于频繁，数据库压力大且收益有限（用户感知不到 1 秒和 60 秒的差别） |
| UV 用 Redis Set | 内存随 UV 线性增长，1 亿 UV 需要 6.4 GB |
| UV 用位图（Bitmap）+ 哈希 | 需要预先确定哈希空间，且哈希冲突会低估 UV；HyperLogLog 更省心 |
| 统计写入本地内存 + 定时批量落库 | 应用重启会丢失未落库数据；多实例下各实例各算各的 |
