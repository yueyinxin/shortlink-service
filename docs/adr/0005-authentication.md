# ADR-0005: 认证采用「短期 JWT + Redis 存储的一次性 Refresh Token」

- **状态**：已接受
- **日期**：2026-09-24
- **相关**：US-02, US-03, AC-03.2, AC-03.3

## 背景

需要选择认证方案。已知的两种主流路线各有明显缺陷：

**纯 Session（服务端存会话）**

- 优点：天然支持撤销（删掉 session 即失效）。
- 缺点：需要共享存储（否则无法水平扩展）；每个请求查一次会话存储。

**纯 JWT（无状态）**

- 优点：服务端不存储，天然支持水平扩展，验证只需本地验签。
- 缺点：**签发后无法撤销**。用户登出、密码被改、令牌泄露，在令牌自然过期前都依然有效。这是 JWT 最被诟病的缺陷。

需要同时满足：可水平扩展（无状态验证）+ 可撤销（登出后立即失效）。

## 决策

采用 **双令牌** 方案：

| 令牌 | 格式 | 有效期 | 服务端存储 | 用途 |
| --- | --- | --- | --- | --- |
| Access Token | JWT（HS256） | 30 分钟 | **不存** | 每次业务请求携带 |
| Refresh Token | 随机 UUID | 14 天 | **存 Redis** | 仅用于换取新的 access token |

关键规则：

1. **Refresh Token 一次性使用**：每次刷新都签发新的 refresh token，并立即删除旧的（Redis `GETDEL` 保证原子性）。使用已消费的令牌会返回 401。
2. Access Token 只包含 `sub`（用户ID）、`username`、`exp`、`jti`，**不包含任何权限或敏感信息**。
3. 登出时删除 Redis 中的 refresh token。
4. 密码修改时（未来功能）删除该用户所有 refresh token。

## 理由

### 为什么这个组合解决了"JWT 不可撤销"

关键在于**把撤销能力放在刷新环节，而不是校验环节**：

- **高频路径（业务请求）** 只验签 access token，不查 Redis —— 保持无状态、零存储访问的性能优势。
- **低频路径（刷新）** 查 Redis 并删除旧令牌 —— 撤销在这里生效。

攻击者拿到 access token，最长只能用到 30 分钟后。而 30 分钟的窗口是通过**缩短 access token 寿命**换来的，代价是用户需要更频繁地刷新（由客户端自动完成，用户无感）。

**这是个有意识的权衡**：我们不追求"泄露后立即失效"（那需要每个请求查 Redis，退化成 Session 方案），而是把损失窗口压缩到 30 分钟。这个窗口是显式选择的，而不是被忽略的。

### 为什么 refresh token 不用 JWT

如果 refresh token 也是 JWT，就无法做到"一次性使用"——JWT 是自包含的，服务端无法知道它是否已被消费过（除非查存储，那就失去了 JWT 的意义）。

用随机 UUID + Redis 存储，可以直接利用 Redis 的原子操作实现一次性消费：

```java
// GETDEL 是原子操作，并发下只有一个请求能拿到值
String userId = redis.opsForValue().getAndDelete(refreshKey(token));
```

**为什么必须用 `GETDEL` 而不是 `GET` + `DELETE`**：两步操作之间存在竞态窗口。两个并发请求可能都 `GET` 到值（都认为令牌有效），然后都 `DELETE`。结果是同一个 refresh token 被用了两次，正是重放攻击要防的情况。`GETDEL` 在 Redis 中是单条原子命令，从根上消除这个窗口。

### 关于 access token 不包含权限信息

把 `role` 放进 JWT 是一个常见做法，本项目**不做**，原因：

- 权限变更后，已签发的 JWT 中的权限仍是旧的，要等最长 30 分钟才生效。这与"JWT 不可撤销"是同一个问题，只是换了个字段。
- v1.0.0 没有角色概念（见需求文档 §3），放进去是无用的冗余。

如果未来引入角色，正确的做法是在每次请求时根据 `userId` 查询权限（带缓存），而不是信任 JWT 中的声明。

### 关于签名算法选择 HS256

- **HS256（对称）**：所有实例共享同一个密钥。适合单体或少量实例的服务。
- **RS256（非对称）**：私钥签发、公钥验证。适合验证方与签发方分离的场景（如微服务、第三方接入）。

本项目是单体服务，签发与验证是同一个应用，HS256 足够且更快。**如果未来拆分为微服务，或需要让第三方独立验证令牌，应切换到 RS256** —— 那时公钥可以安全地分发给验证方，而 HS256 分发密钥等于分发签发能力。

密钥通过环境变量注入（`SHORTLINK_JWT_SECRET`），不写入配置文件或代码。

## 后果

### 正面

- 业务请求零存储访问，可水平扩展。
- 登出、令牌泄露后可在 30 分钟内失效全部会话。
- Refresh token 一次性使用，重放攻击无效。
- 令牌泄露的损失窗口有明确上界（30 分钟），且这个数字是配置项。

### 负面（接受的代价）

- Access token 泄露后最长有 30 分钟的有效窗口。这是被显式接受的权衡。缩短到 5 分钟会更安全，但刷新频率提高 6 倍，需要客户端处理好并发刷新（多个请求同时发现令牌过期时只发起一次刷新）。
- 客户端实现比单一令牌复杂：需要处理"access 过期 → 自动刷新 → 重放原请求"的逻辑。
- Redis 存储 refresh token 意味着 Redis 故障时用户无法刷新令牌（但已登录用户仍可在 access token 有效期内继续使用）。
- 密钥轮换（更换 `JWT_SECRET`）会使所有已签发的 access token 立即失效，用户需要重新登录。这是可接受的，且是密钥泄露时的应急手段。

## 替代方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 纯 Session + Redis | 每个请求查 Redis，性能差；且本质上不是"无状态"，水平扩展依赖共享存储 |
| 纯 JWT（无 refresh token） | **无法撤销**。登出后令牌仍然有效，安全上不可接受 |
| JWT + 黑名单 | 需要为每个被撤销的令牌维护黑名单，且每个请求都要查黑名单——既失去了无状态优势，又比双令牌复杂 |
| 长期 JWT（如 7 天） | 泄露后的损失窗口过大 |
| OAuth2 / 第三方登录 | 本项目不面向第三方接入，也不需要 SSO。引入 OAuth2 授权服务器的复杂度完全不必要 |
| 把 refresh token 也做成 JWT + Redis 记录 | 冗余。既然已经存了 Redis，JWT 的自包含特性没有用武之地，反而使令牌更长 |
