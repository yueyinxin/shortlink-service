# 开发流程说明

| 版本 | v1.0.0 |
| --- | --- |
| 目的 | 说明一个正式项目从需求到上线要经历哪些环节、每个环节产出什么、以及为什么需要这些产物 |

---

## 0. 先看结论：流程的全貌

```
① 立项          ② 设计            ③ 准备            ④ 开发
明确做什么        明确怎么做          搭好地基          按特性迭代
   │                │                  │                │
   ▼                ▼                  ▼                ▼
需求规格          架构设计            仓库与规范         功能分支
用户故事 +        分层与依赖           .gitignore        小步提交
验收标准          ADR 决策记录         CI 流水线         PR 评审
范围外清单        数据库设计           本地环境          测试
   │                │                  │                │
   └────────────────┴──────────────────┴────────────────┘
                              │
                              ▼
⑤ 质量           ⑥ 交付           ⑦ 上线           ⑧ 维护
  测试策略          文档             部署              监控
  单元/集成          README           环境变量         告警
  覆盖率            部署手册          健康检查         故障响应
  架构约束测试      变更日志          回滚方案         技术债
```

**核心认知：代码只是流程的产物之一，而不是全部。**

一个只有代码的项目和一个有完整流程的项目，差别不在于"谁写得更好"，而在于：

- 前者的问题是**不可见**的（没人知道范围边界在哪、为什么这样设计、出问题怎么查）
- 后者的每个决定都**留下了痕迹**，后来的维护者能理解而不是猜测

## 1. 立项阶段：明确做什么（以及不做什么）

### 1.1 产物

| 产物 | 本项目文件 | 作用 |
| --- | --- | --- |
| 需求规格说明书 | [`docs/01-requirements.md`](01-requirements.md) | 定义目标、角色、范围、验收标准 |
| 范围外清单 | 同上 §2.2 | 明确列出**不做什么**及原因 |

### 1.2 关键做法

**用户故事 + 可执行的验收标准**

需求不写成"系统应支持短链跳转"，而写成：

> **作为**一名点击短链的访客，**我希望**被正确重定向到目标页面。

然后附上验收标准（Given-When-Then）：

> **AC-05.5** Given 跳转成功，When 检查响应，Then **响应时间不包含统计写入的耗时**（统计必须异步化）。

**为什么必须这样写**：验收标准是需求与测试之间的桥梁。
"系统应支持短链跳转"无法直接翻译成测试用例，而 AC-05.5 可以直接翻译成一个集成测试。
**写不出验收标准的需求，说明还没有想清楚。**

**必须显式写出范围外事项**

本项目在需求文档中列出了 7 项"明确不做"的功能，每项都标注了原因和后续计划：

| 项 | 原因 | 后续计划 |
| --- | --- | --- |
| 访问密码保护 | 需求优先级低 | v1.2 |
| IP 归属地解析 | 需引入离线 IP 库（数十 MB） | v1.3 |
| 多租户 / 团队协作 | 需要重构权限模型 | v2.0 |

> **为什么这一步比"要做什么"更重要**：项目的失控几乎从不来自"少做了一个功能"，
> 而是来自"什么都在做"。范围外清单是抵御范围蔓延的书面依据 ——
> 当有人提出新需求时，可以指着它说"这一项我们讨论过，当时的结论是 v1.2 再做"。

**非功能需求必须绑定验证方式**

| 类别 | 需求 | 验证方式 |
| --- | --- | --- |
| 性能 | 跳转接口缓存命中 P99 < 50 ms | 压测（JMeter/wrk） |
| 可用性 | Redis 故障时跳转降级可用 | 集成测试中停掉 Redis 验证 |

写不出验证方式的指标（例如"系统要快"）不是需求，是愿望。

## 2. 设计阶段：明确怎么做

### 2.1 产物

| 产物 | 本项目文件 | 作用 |
| --- | --- | --- |
| 架构设计说明书 | [`docs/02-architecture.md`](02-architecture.md) | 分层、依赖规则、核心链路、安全设计、**已知风险** |
| 架构决策记录（ADR） | [`docs/adr/`](adr/) | 每个关键选择的背景、决策、理由、**放弃的替代方案** |
| 数据库设计说明书 | [`docs/03-database-design.md`](03-database-design.md) | ER 图、索引依据、关键取舍 |

### 2.2 关键做法：ADR

ADR（Architecture Decision Record）是设计阶段最有价值的产物，格式很简单：

```markdown
# ADR-0002: 短码采用 Feistel 格式保留加密打散自增序列

- 状态：已接受
- 日期：2026-09-24

## 背景
（面临什么问题，有哪些约束）

## 决策
（决定了什么）

## 理由
（为什么这样决定，与替代方案的对比）

## 后果
### 正面
### 负面（我们接受的代价）

## 替代方案与放弃原因
（考虑过什么，为什么没选）
```

**为什么 ADR 比架构文档更有价值**：架构文档描述"现在是什么样"，
而 ADR 记录了"**为什么是这样**"以及"**曾经考虑过什么别的方式**"。

半年后有人问"为什么不用随机生成短码"，如果只有代码，答案只能靠猜测；
如果有一篇 ADR，答案就在那里，包括当时权衡的两面。

**本项目 ADR 中最值得看的一篇**：[ADR-0002](adr/0002-short-code-generation.md)。
它完整记录了一次**设计评审发现并否决自己方案**的过程 ——
最初选的线性同余打散在数学上同样无冲突，但相邻输出的差值恒为常数，
攻击者可以解方程还原整个映射。这个缺陷现在被一条回归测试守护。

> **流程启示**：设计评审要推演**攻击者视角**，而不只是验证"功能是否正常"。
> "功能正常"和"安全"是两个独立的检验维度。

### 2.3 关键做法：诚实记录已知风险

本项目的架构文档有一节「已知架构风险」，列出了 6 项当前设计的弱点：

| 风险 | 触发条件 | 影响 | 预案 |
| --- | --- | --- | --- |
| 统计任务不支持多实例 | 部署 > 1 个实例 | 任务重复执行，PV 翻倍 | 引入分布式锁 |
| 短码空间耗尽 | 生成量 > 568 亿 | 打散后回绕，产生冲突 | 扩展为 7 位 |

**不写风险的架构文档是不完整的。** 把"当前单实例部署下统计任务不会重复执行"
这个隐含假设显式写出来，比假装它不存在要有用得多 ——
因为下一个部署的人很可能不知道这个假设。

## 3. 准备阶段：搭好地基

### 3.1 产物

| 产物 | 本项目文件 | 作用 |
| --- | --- | --- |
| `.gitignore` | `.gitignore` | 排除构建产物**与密钥文件** |
| 贡献指南 | [`CONTRIBUTING.md`](../CONTRIBUTING.md) | 分支模型、提交规范、代码规范、测试要求 |
| CI 流水线 | [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) | 每次推送自动构建与测试 |
| Issue / PR 模板 | `.github/ISSUE_TEMPLATE/`、`.github/pull_request_template.md` | 结构化信息收集 |
| 本地环境编排 | [`compose.yaml`](../compose.yaml) | 一条命令启动依赖服务 |
| 许可证 | [`LICENSE`](../LICENSE) | 明确使用条款 |

### 3.2 关键做法：`git init` 之前先想清楚忽略什么

本项目 `.gitignore` 中有一行值得单独说明：

```gitignore
### 项目特有 ###
# 部署密钥文件。绝不能进入版本库 —— 一旦提交，即使后续删除
# 也仍然能从 git 历史中恢复，唯一补救办法是更换全部密钥。
deploy/.env
```

**为什么这条注释比规则本身重要**：规则的效力来自理解。
不知道"为什么不能提交密钥"的人，会在某次紧急修复时把它加上去。

**另一个容易忽略的点**：`.gitignore` 必须在第一次提交前就配好。
如果先提交了构建产物或密钥，后续即使加到 `.gitignore` 也不会把它们从历史中移除。

### 3.3 关键做法：CI 从第一天就存在

本项目在脚手架搭好后立刻配置了 CI，而不是等到功能开发完。

**理由**：CI 的价值在于**持续**提供反馈。等到功能都写完再加，
既失去了过程中的保护，也会一次性暴露大量被忽视的问题，修复成本远高于逐步修复。

CI 的设计也有讲究：

- **`concurrency` 配置**：同一分支的旧运行在新提交到来时自动取消。
  没有它，连续推送几次会让多个流水线并行执行。
- **单元测试与集成测试分离**：`mvn test` 保持秒级反馈（不依赖 Docker），
  `mvn verify` 才启动 Testcontainers。这让开发者在写代码时的循环足够快。
- **镜像构建后做冒烟测试**：只构建不运行的检查是不够的 ——
  一个缺少 JRE 或入口脚本错误的镜像同样能构建成功。

## 4. 开发阶段：按特性迭代

### 4.1 产物

| 产物 | 说明 |
| --- | --- |
| 功能分支 | `feature/xxx`，从 `main` 切出 |
| 规范提交 | Conventional Commits，正文说明**为什么** |
| Pull Request | 附带自查清单（含安全检查项） |
| 测试 | 新增逻辑必须有对应测试 |

### 4.2 关键做法：小步提交，每次提交都是可工作的

本项目把开发切成 7 个特性阶段，每个阶段独立可验证：

```
feat(common): 建立统一响应与错误码体系
feat(link): 实现 Feistel 短码生成器
feat(link): 实现短链跳转与 Redis 缓存
feat(stats): 实现访问统计与定时刷库
...
```

**为什么不一次性提交所有代码**：一个包含 60 个文件的提交是无法评审的。
评审者只能在"看不过来"和"不看了直接批准"之间选一个，两者都等于没有评审。

而按特性切分的提交，每个都小到可以真正读懂。

### 4.3 关键做法：提交信息必须写"为什么"

对比这两种写法：

```
fix: 修复登录接口的问题
```

```
fix(auth): 抹平账号不存在与密码错误的响应时间差

原先用户不存在时直接返回，跳过了 BCrypt 校验，响应明显更快。
攻击者通过测量响应时间就能判断某个用户名是否已注册。

修复方式是在用户不存在时也执行一次针对占位哈希的比对。占位哈希对应一个
随机生成的、无人知晓的密码，因此永远不可能匹配成功。

关联 #57
```

**diff 本身已经说明了"改了什么"。唯一无法从代码中恢复的信息是"为什么"** ——
为什么选这个方案、当时的约束是什么、否决了哪些替代方案。

缺少这些，后来的维护者只能靠猜测，而猜错的代价通常是重复踩同一个坑 ——
甚至可能把一个精心设计的保护性检查当作冗余代码删掉。

### 4.4 关键做法：测试先于修复

修复缺陷时，**先写一个能复现该缺陷的测试，确认它失败，再修复**。

没有复现测试的修复有两个问题：

1. **无法证明问题被解决了**。"改完看起来好了"和"确定好了"是两件事。
2. **无法防止它被重新引入**。三个月后有人重构这段代码，没有任何东西会提醒他。

本项目的 [`HttpUrlValidatorTest`](../src/test/java/io/github/yueyinxin/shortlink/common/validation/HttpUrlValidatorTest.java)
就是这个思路的产物：它守护的是一条**安全控制**（协议白名单，防止服务成为 XSS 跳板），
任何放宽白名单的改动都会让它变红。

## 5. 质量阶段：测试策略

### 5.1 产物

| 层次 | 命名 | 执行时机 | 特点 |
| --- | --- | --- | --- |
| 单元测试 | `*Test.java` | `mvn test` | 不起 Spring 上下文，毫秒级 |
| 集成测试 | `*IT.java` | `mvn verify` | 真实 MySQL / Redis |
| 架构测试 | `ArchitectureTest` | `mvn test` | 用 ArchUnit 校验分层依赖 |

### 5.2 关键做法：测试金字塔要真的落地

本项目的测试分布：

```
        ▲  集成测试（*IT）        少量、慢、验证真实依赖
       ╱ ╲
      ╱   ╲
     ╱─────╲  单元测试（*Test）    多量、快、覆盖分支与边界
    ╱       ╲
   ╱─────────╲  架构约束测试        少量、守护结构不腐化
```

关键在于**让单元测试真正覆盖核心逻辑**，而这需要架构的配合：
只有当领域逻辑不依赖框架时，它才能被快速测试。

本项目的 `ShortCodeGenerator` 是一个纯函数（无随机、无 IO、无 Spring），
因此它的测试可以在毫秒内完成，并且能写出这样的断言：

> 在 4 位短码空间上穷举全部 **14,776,336 个**序列号，验证映射是置换（无重复、无遗漏）。

**这种测试只有在设计阶段就把逻辑与框架解耦才写得出来。**

### 5.3 关键做法：不要用 H2 做集成测试

H2 与 MySQL 在 `ON DUPLICATE KEY UPDATE` 语法、`LIMIT` 分页、字符集与排序规则、
`DATETIME` 精度上都有差异。在 H2 上通过的测试**不能保证** MySQL 上也通过 ——
**这类"假绿"测试比没有测试更危险**，因为它让人对结论产生错误的信心。

本项目的选择：用 Testcontainers 启动真实 MySQL 8.0。
代价是首次运行需要拉取约 600MB 镜像，因此放在 `*IT.java` 中由 `mvn verify` 执行。

### 5.4 关键做法：架构约束必须能被自动验证

本项目的 `ArchitectureTest` 用 ArchUnit 断言了 5 条分层规则，例如：

```java
noClasses()
    .that().haveSimpleNameEndingWith("Controller")
    .should().dependOnClassesThat().haveSimpleNameEndingWith("Repository")
    .because("控制器必须经过服务层，否则会绕过事务边界与归属校验");
```

**这条测试在本次开发中真的抓到了一个违规**：限流过滤器需要读取认证上下文中的用户身份，
却被我放在了"通用工具"包里，形成了 `common → auth` 的反向依赖。

修复方式不是放宽规则，而是**修正包划分** —— 那个过滤器本来就不是通用工具，
而是一个依赖安全上下文的安全组件。规则揭示的是真实的设计问题。

> **核心认知：架构约束必须能被自动验证，否则一定会被违反。**
> 违反几乎从不是有意的，通常是赶功能时的"就这一处"。
> 而如果没人能自动发现，它就会一直累积到某天想给核心逻辑补测试时，
> 发现必须启动整个 Spring 上下文。

## 6. 交付阶段：文档与部署

### 6.1 产物

| 产物 | 本项目文件 | 作用 |
| --- | --- | --- |
| README | [`README.md`](../README.md) | 项目门面：是什么、怎么跑、为什么这样设计 |
| 部署编排 | `deploy/compose.prod.yaml` | 生产环境的完整栈 |
| 部署脚本 | `deploy/deploy.sh` | 一键部署与状态检查 |
| 环境变量模板 | `deploy/.env.example` | 需要配置什么，以及为什么 |
| 变更日志 | [`CHANGELOG.md`](../CHANGELOG.md) | 每个版本改了什么 |
| 面试讲解手册 | [`docs/08-interview-guide.md`](08-interview-guide.md) | 项目的自查与讲解顺序 |

### 6.2 关键做法：README 要能让人 5 分钟跑起来

README 的第一屏决定读者是否继续往下看。本项目的组织结构：

1. **一句话说明这是什么**
2. **快速开始**（前置要求 + 三步启动 + 可直接复制的 curl 命令）
3. **核心设计**（三个最有技术含量的点）
4. 架构、接口、项目结构、技术栈
5. **已知限制**（诚实列出边界）
6. 文档导航

### 6.3 关键做法：让配置错误在启动时暴露

生产配置有两层保护，避免带着开发默认值上线：

1. `application-prod.yml` 中的敏感项**没有默认值**（`${VAR}` 而非 `${VAR:default}`），
   缺少环境变量时应用无法启动。
2. `StartupSafetyCheck` 在启动完成后检查配置，检测到开发默认密钥则**拒绝启动**，
   并打印具体是哪个变量。

**为什么选择"拒绝启动"而不是"打警告"**：带着公开可知的默认密钥运行，
比启动失败严重得多。启动失败会立刻被运维发现，而密钥泄露可能几个月都无人察觉。

## 7. 上线与维护阶段

### 7.1 产物

| 产物 | 本项目实现 |
| --- | --- |
| 健康检查 | `/actuator/health`（区分存活与就绪探针） |
| 监控指标 | `/actuator/prometheus`（HTTP 耗时直方图、JVM 指标） |
| 链路追踪 | `TraceIdFilter` 为每个请求注入 traceId，贯穿所有日志 |
| 回滚能力 | 镜像 tag 化部署，`deploy.sh --no-build` 可用旧镜像重启 |
| 技术债记录 | 架构文档的「已知风险」表 + 需求文档的「范围外」表 |

### 7.2 关键做法：可观测性从设计阶段就要考虑

本项目在设计阶段就确定了：

- 日志每行都带 `traceId`，一个请求产生的所有日志可以串起来
- 500 响应只返回通用文案，**绝不回显 `ex.getMessage()`**
  （数据库连接串、SQL 片段经常出现在异常消息里）
- 4xx 业务异常**不打堆栈**（每天发生无数次，打堆栈会淹没真正的故障）

最后一条体现了一个重要判断：**日志的价值在于信噪比，而不在于数量。**
把"用户输错密码"和"数据库连接失败"记录成同样详细的程度，
等于让真正需要关注的信号消失在噪声里。

### 7.3 关键做法：技术债要写下来，而不是记住

本项目的技术债放在两个地方：

- 架构文档的「已知风险」表：每项有触发条件、影响、预案
- 需求文档的「范围外」表：每项有原因、后续计划

**为什么不能只记住**：人会离职，记忆会模糊。
写在文档里的技术债，在新成员加入时是**上下文**；
只存在于某人脑中的技术债，是**一颗定时炸弹**。

## 8. 本项目流程的自我评估

诚实评价这套流程在这个项目上的执行情况：

| 阶段 | 完成度 | 说明 |
| --- | --- | --- |
| 立项 | 完整 | 需求、范围外清单、验收标准齐备 |

**最后两行的空缺是客观事实，应当如实说明。**
"上线"和"维护"这两个阶段的经验只能从真实运行中获得，
而它们恰好是最能体现工程能力的部分。

面试时主动说明这一点，比假装项目已经承载了生产流量要好得多 ——
后者只要被追问一句"线上 QPS 多少、遇到过什么故障"就会暴露。

## 9. 一页速查：每个阶段的最小产物

如果时间有限，只做这些：

| 阶段 | 最小产物 | 一句话理由 |
| --- | --- | --- |
| 立项 | 一页需求 + **范围外清单** | 范围蔓延是项目失控的头号原因 |
| 设计 | 一张架构图 + **关键决策的 ADR** | ADR 记录的是唯一无法从代码恢复的信息 |
| 准备 | `.gitignore` + **CI** | CI 的价值在于持续，晚加等于白加 |
| 开发 | **规范提交** + 测试 | 提交信息是给未来的维护者看的 |
| 质量 | 核心逻辑的**单元测试** + 边界条件 | 覆盖率数字不重要，"覆盖了什么"才重要 |
| 交付 | **能 5 分钟跑起来的 README** | 没人跑起来的项目等于不存在 |
| 上线 | 健康检查 + 日志中的 traceId | 出问题时能定位，比不出问题更现实 |
| 维护 | **写下来的技术债** | 记住的债不存在 |
