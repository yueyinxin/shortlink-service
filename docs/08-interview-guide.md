## 0. 讲解前必须知道的三件事

**第一，不要背项目介绍。** 面试官听过太多"我做了个短链服务，用了 Spring Boot + Redis + MySQL"。
这种开场等于没说 —— 它没有提供任何可以继续追问的信息点，也无法证明你真的理解自己写的东西。

**第二，主动给出"钩子"。** 你的目标是引导面试官问你准备过的问题。
方法是在介绍中埋入有技术含量的细节，让面试官自然想追问。

**第三，主动暴露不足。** 一个声称"没有任何问题的项目"会让人怀疑你没有深入思考。
主动说出已知限制，反而显得可信 —— 但你必须同时给出应对方案。

## 1. 两分钟开场

> 我做过一个短链接服务，它的核心矛盾是**读写特征极不对称**：
> 跳转占总流量 99% 以上且对延迟极敏感，而管理操作频率低、要求强一致。
> 我所有的设计决策都是从这个事实推导出来的。
>
> 有三个点我觉得比较有意思：
>
> **第一，短码生成是数学上无冲突的。** 我没有用常见的"随机生成 + 查重"，
> 而是用 Feistel 网络对数据库自增主键做格式保留加密。Feistel 结构的性质保证了
> 输出必然是双射，所以不同序列号必然产生不同短码 —— 不需要查重、不需要重试、
> 并发下不会失败。我还写了个测试，在 4 位短码空间上穷举了 1477 万个序列号验证这一点。
>
> **第二，跳转路径上没有任何数据库写操作。** 缓存里存的是包含状态和过期时间的完整快照，
> 所以命中缓存就能完成全部判定。访问统计只写 Redis，由定时任务批量落库，
> 查询时再把未落库的增量合并进来。而且 Redis 整个挂掉时，跳转会降级为直查数据库，
> 仍然可用 —— 因为 MySQL 是唯一真相来源，Redis 里的数据全部可重建。
>
> **第三，统计的 PV 和 UV 用了不同的语义。** PV 是增量，取出并清零后累加；
> UV 是绝对值，当日的 HyperLogLog 全程保留，写入时取最大值。
> 因为 HyperLogLog 无法做差集，如果 UV 也用增量累加，
> 同一个访客在多次刷库中会被重复计数。

**为什么这样开场**：三个点分别对应并发、缓存架构、数据结构选择，
都是面试官关心的方向，且每个点都有可以继续深挖的层次。
同时"穷举 1477 万个序列号"这种具体数字，会让面试官相信你真的做了这件事。

## 2. 高频追问与参考回答

### 2.1 关于短码生成

**Q：为什么不用随机生成 + 唯一索引 + 重试？那样实现简单多了。**

> 随机方案的问题是**并发下的竞态**：两个请求可能同时随机到同一个短码，
> 都查重通过（因为对方还没提交），然后其中一个因唯一索引冲突而失败。
> 这表现为线上偶发的创建失败，且难以复现 —— 需要精确的时序重合。
>
> 而且冲突率随占用率上升：空间占用 50% 时，平均要试 2 次。
> 相比之下 Feistel 方案的无冲突是数学保证，不是概率保证。

**Q：Feistel 为什么是双射？**

> 因为每一轮的结构是 `(L, R) ← (R, L ⊕ F(R))`。
> 这个变换本身可逆：给定 `(L', R')`，可以恢复出 `R = L'` 和 `L = R' ⊕ F(L')`。
> 关键是**轮函数 F 不需要可逆** —— 整个网络的可逆性来自左右交换的结构。
> 所以只要 F 是确定的，8 轮迭代下来必然是双射。

**Q：62^6 不是 2 的幂，怎么在 Feistel 上处理？**

> 用 Cycle-Walking，这是格式保留加密里处理非 2 的幂定义域的标准技术。
> 我在 36 位分组上做置换（2^36 > 62^6），如果结果落到有效区间之外就再置换一次，
> 直到落入为止。期望迭代次数是 62^6 / 2^36 ≈ 1.21 次，代价可忽略。
> 正确性上，因为 Feistel 是 2^36 上的置换，
> 把它的一个轮换限制在子集 [0, 62^6) 上仍然是置换。

**Q：这个方案有什么缺点？**

> 有两个。一是**依赖数据库自增主键**，所以创建流程要先 INSERT 拿到主键、
> 再 UPDATE 回填短码，多一次写入。相对于"无冲突"带来的收益，这个代价可以接受。
>
> 二是**短码空间耗尽后会回绕产生冲突**。当前 6 位空间是 568 亿，
> 按每天 100 万条新增可以用 1500 多年，但这是需要监控的水位 ——
> 接近 80% 时应该扩展为 7 位。

**Q：这个方案你是一开始就想到的吗？**

> 不是。我最初用的是线性同余打散 `(seq × A + B) mod 62^6`，
> 它在 `gcd(A, 62^6) = 1` 时同样双射，而且实现只要一行。
>
> 但后来推演攻击者视角时发现问题：线性同余映射的**相邻输出差值恒为 A**。
> 攻击者连续创建几个短链，把短码解码后相邻相减，就能解出 A 和 B，
> 进而还原整个映射、枚举全站短码。
>
> 这是一个把**混淆当成加密**的典型错误 —— Base62 编码在视觉上打乱了数字，
> 但底层的线性结构完好无损。"看起来乱"不等于"不可枚举"。
>
> 修正后我保留了这个教训：现在有一条回归测试专门断言"相邻短码的数值差不是常数"，
> 如果有人改回线性变换，测试会立刻失败。

**为什么这样回答这个"送分题"**：面试官问"是不是一次做对的"，
往往是想看你有没有真实的设计迭代过程。承认走过弯路并说明如何发现和修正，
比声称一次成功要可信得多。同时展示了你具备"主动推演攻击者视角"的意识。

### 2.2 关于缓存

**Q：缓存里为什么存整个对象，只存 URL 字符串不行吗？**

> 只存 URL 会导致一个隐蔽的问题：跳转前要判断短链是否过期或被禁用，
> 这两个字段不在缓存里，就必须回查数据库。**缓存命中却仍要访问数据库，缓存就失去了意义**。
>
> 缓存整个快照后，命中缓存即可完成全部判定，热路径零数据库访问。

**Q：先更新数据库再删缓存，为什么不直接更新缓存？**

> 两个原因。
>
> 一是**并发下更容易出错**：更新缓存需要把新状态完整计算一遍，
> 而并发读请求可能在计算过程中把旧值写回，造成长期不一致。
> 删除缓存则是幂等的、无条件正确的操作 —— 它只是让下次读去数据库取。
>
> 二是**顺序问题**：先删缓存再更新数据库，会有"删缓存 → 更新DB"的窗口，
> 期间读请求把旧值写回缓存并长期留存。
> 先更新DB再删缓存也有窗口，但要窄得多，且下一次读就会修复。

**Q：那为什么不用延迟双删？**

> 延迟双删能进一步压低不一致窗口，但它引入两个新问题：
> 延迟时间无法科学确定（500ms 是拍脑袋的），以及一次几乎总是无用的额外删除。
>
> 本场景的缓存是**只读为主、极少更新**的 —— 用户很少修改已创建的短链。
> 不一致窗口最长只有"更新DB到删缓存"的几毫秒。
> 为此引入延迟双删的复杂度不划算。

**Q：缓存穿透和雪崩怎么处理的？**

> 穿透用**空值缓存**：查询不存在的短码时，也缓存一个特殊标记，TTL 60 秒
> —— 显著短于正常缓存的 24 小时，因为过长的空值缓存会让"刚创建就访问"的短链误报 404。
>
> 雪崩用 **TTL 随机抖动**：正常缓存的 TTL 是 24 小时 ± 10% 的随机值。
> 如果所有短链 TTL 相同，批量导入的短链会在同一秒集中过期，全部请求穿透到数据库。
>
> 我没有引入布隆过滤器。它需要维护一个与数据库同步的位图，
> 而短链删除后无法从布隆过滤器移除条目（需要重建或改用计数布隆过滤器）。
> 当前空值缓存 + 限流已经覆盖了穿透攻击的主要场景。
> 我把它记为"有意的先不做"，等压测证明空值缓存不足时再引入。

**Q：Redis 挂了怎么办？**

> 降级为直查数据库，跳转仍然可用，只是变慢。
>
> 这是可用性设计的核心：**MySQL 是唯一真相来源，Redis 里的数据全部可重建**。
> 所以 Redis 是性能组件，不是可用性单点。
>
> 实现上所有 Redis 操作都被捕获并降级为"缓存未命中"，而不是向上抛异常 ——
> 让异常传播的话，一个小概率的缓存抖动就会变成用户可见的 500。
> 降级分支都打 WARN 日志，因为"服务正在以降低的性能运行"这个事实需要在监控上可见。

### 2.3 关于统计

**Q：为什么不用消息队列？异步统计不是应该用 MQ 吗？**

> 这是我刻意没做的一件事。MQ 是异步统计的标准方案，但它引入的成本很高：
> 多一个中间件要部署监控调优、要处理消息丢失和重复消费、本地开发环境变成必须起 4 个容器。
>
> 而本场景的真实需求只是"延迟不超过 60 秒的最终一致"，
> Redis + 定时任务用**一个已经存在的组件**就满足了。
> 本地开发只需要 MySQL + Redis 两个容器。
>
> **取舍点在于**：如果将来需要"精确到每次访问的明细流水"（比如风控审计），
> 或者统计写入量超过 Redis 单实例吞吐，那就必须引入 MQ。
> 当前需求是按天聚合的 PV/UV，不需要。

**Q：UV 为什么用 HyperLogLog？误差能接受吗？**

> 用 Set 记录所有访问过的 IP，内存占用与独立 IP 数成正比：
> 1 亿 UV 需要约 6.4 GB，而 HyperLogLog 固定只需 12 KB，标准误差 0.81%。
>
> 对于"评估投放效果"这个场景，100 万 UV 有 ±8100 的误差完全不影响决策 ——
> 运营需要知道的是"这次投放带来了 10 万还是 100 万访问"，不是精确到个位数。
>
> 我在需求文档的验收标准里明确写了 ±1 的容差，而不是假装精确。
> 代价是 HLL 无法删除单个元素、无法列举成员，本项目不需要这两个能力。

**Q：为什么 PV 和 UV 的更新方式不同？**

> PV 用增量累加，UV 用 `GREATEST` 取最大值。
>
> 原因是 **HyperLogLog 无法做差集**。如果 UV 也用增量语义 ——
> 每次刷库取出估值并累加 —— 同一天内跨多次刷库出现的重复 IP 会被重复计数。
> 举例：同一访客 10 点和 11 点各访问一次，两次刷库各得 UV=1，
> 累加后当天 UV=2，而正确答案是 1。
>
> 正确做法是让 HLL 在当天全程保留，每次刷库读取它的当前完整估值并取 max 写入。
> 因为 HLL 始终代表"当天至今的全部独立访客"，重复写入同一个值是无害的。

**Q：刷库任务怎么知道哪些短链有待落库的数据？**

> 扫描 Redis 键。这里有个坑：**不能用 `KEYS`**，它会遍历整个键空间且阻塞 Redis 的
> 所有其他命令。在有几十万短链的实例上执行一次足以造成数百毫秒的服务停顿，
> 而这个任务每 60 秒执行一次 —— 等于每 60 秒制造一次人为的延迟毛刺。
>
> 我用 `SCAN` 游标分批遍历，不阻塞其他命令。
> 代价是遍历过程中新加入的键可能被遗漏或重复返回。
> 遗漏的键会在下一轮处理，而重复处理是安全的 ——
> 因为 PV 的"取出并清零"是原子操作，UV 写入取 max 幂等。

**Q：刷库为什么必须原子？**

> 如果实现成"先读、再删"两步，两次刷库之间可能读到相同的计数并重复累加，
> PV 会翻倍。这类 bug 只在特定时序下出现，常规测试很难覆盖，而且发现时数据已经错了。
>
> 我用 Lua 脚本实现"取值并清零"，脚本在 Redis 中单线程原子执行。

**Q：查询时用户看到的数据是最新的吗？**

> 是最新的。虽然刷库有最长 60 秒延迟，但查询时会**合并 Redis 中尚未落库的增量**：
>
> ```
> pv = 数据库已落库值 + Redis 待落库增量
> uv = max(数据库已落库值, Redis 当日 HLL 估值)
> ```
>
> 这个公式对当天和历史日期都成立，不需要分支 ——
> 历史日期的 Redis 键已被删除，`readPv` 返回 0、`readUv` 返回 0，
> 公式自然退化为"pv = 数据库值"、"uv = 数据库值"。

### 2.4 关于安全

**Q：短链服务有什么安全问题？**

> 最严重的是**开放重定向**。如果我不限制协议，攻击者可以创建指向
> `javascript:alert(document.cookie)` 的短链。因为跳转发生在**我服务的域名下**，
> 浏览器会认为这是可信来源 —— 这让服务变成 XSS 和钓鱼的跳板，
> 而受害者看到的域名是我们的。
>
> 所以我在 DTO 校验上做了协议白名单，只允许 http 和 https。
> 这不是格式校验，是安全控制。
>
> 另外我在跳转路径上加了一道**纵深防御**：即使数据库里的 URL 被绕过校验写入
> （历史数据、人工改库、迁移脚本错误），跳转前也会再检查一次协议前缀。
> 代价是一次 `startsWith` 比较，纳秒级。
>
> 其他还有：越权访问返回 404 而非 403（避免泄露"该短码存在"）、
> 分页 size 上限 100（防止 `size=1000000` 拉爆内存）、
> Actuator 只放行 health（`/actuator/env` 和 `/actuator/heapdump` 会泄露配置和内存中的凭证）。

**Q：登录接口怎么防用户名枚举？**

> 有两种枚举方式，我都处理了。
>
> **错误信息枚举**：用户不存在和密码错误返回**完全相同**的错误码和文案。
> 如果区分开来，攻击者可以用任意密码试探，根据错误信息筛出已注册的用户名。
>
> **计时枚举**：这个更隐蔽。用户不存在时如果直接返回，跳过了 BCrypt 校验，
> 响应会明显快于用户存在的情况（省了一次约 100ms 的计算）。
> 攻击者通过测量响应时间就能判断某个用户名是否已注册。
>
> 修复方式是无论用户是否存在都执行一次 BCrypt 比对 ——
> 用户不存在时拿一个占位哈希去比。占位哈希对应一个随机生成的、无人知晓的密码，
> 永远不可能匹配成功。代价是每次失败登录都要付一次 BCrypt 成本，
> 而这个成本本身也是一种保护（暴力破解更慢）。

**Q：JWT 无法撤销，你怎么处理的？**

> 我用的是双令牌方案：短期 access token + Redis 存储的一次性 refresh token。
>
> 关键思路是**把撤销能力放在刷新环节，而不是校验环节**。
> 高频的业务请求只验签 access token，不查 Redis —— 保持无状态的性能优势。
> 低频的刷新操作查 Redis 并删除旧令牌 —— 撤销在这里生效。
>
> 这样攻击者拿到 access token 最长只能用 30 分钟。
> 这是**有意识的权衡**：我不追求"泄露后立即失效"（那需要每个请求查 Redis，
> 退化成 Session 方案），而是把损失窗口压缩到 30 分钟。
>
> refresh token 是一次性的，用 Redis 的 `GETDEL` 原子消费。
> 这里必须用原子操作：如果是"GET 再 DELETE"两步，
> 两个并发请求可能都读到值（都认为有效），然后都删除 ——
> 同一个 refresh token 被用了两次，正是重放攻击要防的情况。

**Q：access token 里为什么不放角色权限？**

> 权限一旦签发就无法收回，变更后要等令牌自然过期才生效 ——
> 这和"JWT 不可撤销"是同一个问题，只是换了个字段。
>
> 我当前版本没有角色概念，所以放进去是无用的冗余。
> 如果将来引入角色，正确做法是在每次请求时按 userId 查询权限（带缓存），
> 而不是信任令牌中的声明。

**Q：密码为什么限制最大长度？**

> 两个原因。
>
> 一，**BCrypt 只使用密码的前 72 字节**。不设上限的话，用户以为设了 100 位强密码，
> 实际只有前 72 字节参与计算，而系统不会给出任何提示。
> 这种"看起来更安全实际不然"的落差比直接限制更危险。
>
> 二，BCrypt 的计算时间随密码长度增长。不设上限时，
> 攻击者可以用超长密码让服务端持续做昂贵的哈希运算，构成拒绝服务向量。
>
> 另外我在服务层还检查了 UTF-8 字节长度不超过 72 ——
> 因为 `@Size(max = 64)` 限制的是字符数，而在 UTF-8 下一个中文字符占 3 字节，
> 64 个字符最多可能是 192 字节。

### 2.5 关于架构与工程实践

**Q：为什么按功能切分包，而不是按 controller/service/repository 分层？**

> 决定性因素是**改动的影响半径**。以"给短链增加过期提醒"为例：
> 按技术分层要触碰 4 个顶层目录，而按功能垂直切分只需要在 `link/` 一个目录内改动。
>
> 其次，垂直切分天然约束了**跨功能域的耦合**。在 `link` 包内无法直接 import
> `stats` 的内部类（需要显式跨越包边界），这种摩擦会促使开发者思考依赖是否合理。
> 而在按技术分层的结构里，`LinkService` 调用 `StatsService` 看起来完全正常，
> 耦合会在不知不觉中累积。
>
> 代价是对完全不了解项目的人，"先去哪个包找 Controller"需要先看一眼结构。
> 我认为这个代价可以接受。

**Q：你怎么保证分层约束不被违反？**

> 我用 ArchUnit 写了架构测试，把它变成可执行的断言。
> 比如断言 Controller 不能依赖 Repository、domain 不能依赖框架。
>
> **这条测试在本次开发中真的抓到了一个违规**：限流过滤器需要读取认证上下文中的
> 用户身份，却被我放在了 "通用工具" 包里，形成了 `common → auth` 的反向依赖。
>
> 修复方式不是放宽规则，而是**修正包划分** ——
> 那个过滤器本来就不是通用工具，而是一个依赖安全上下文的安全组件。
> 规则揭示的是真实的设计问题。
>
> 我的核心认知是：**架构约束必须能被自动验证，否则一定会被违反**。
> 违反几乎从不是有意的，通常是赶功能时的"就这一处"。

**Q：为什么集成测试不用 H2？**

> H2 与 MySQL 在 `ON DUPLICATE KEY UPDATE` 语法、`LIMIT` 分页、
> 字符集与排序规则、`DATETIME` 精度上都有差异。
> 在 H2 上通过的测试**不能保证** MySQL 上也通过。
>
> 我管这叫"假绿"测试 —— 它比没有测试更危险，因为它让人对结论产生错误的信心。
>
> 我的选择是用 Testcontainers 启动真实 MySQL 8.0，
> 代价是首次运行要拉 ~600MB 镜像。所以我把集成测试放在 `*IT.java` 中由
> `mvn verify` 执行，而 `mvn test` 只跑不需要外部依赖的单元测试，
> 保持开发时的秒级反馈。

**Q：你怎么测试短码生成的正确性？**

> 我在 4 位短码空间上**穷举了全部 14,776,336 个序列号**，
> 验证映射是一个置换 —— 每个位置恰好被覆盖一次，无重复无遗漏。
>
> 这比"抽样检查不重复"强得多：它证明了映射确实是整个空间上的置换。
> 而且这种测试只有在设计阶段就把逻辑与框架解耦才写得出来 ——
> `ShortCodeGenerator` 是纯函数，无随机、无 IO、不依赖 Spring，
> 所以能在几秒内跑完 1477 万次迭代。

**Q：为什么有些表用 DATETIME(6)？**

> 两层原因。一是**排序稳定性**：`created_at` 用于分页排序，
> 秒精度下同一秒创建的两条记录顺序不确定，会导致同一条记录在第 1 页和第 2 页都出现，
> 或者某条记录完全看不到。
>
> 二是**与 ORM 默认映射一致**：Hibernate 把 `LocalDateTime` 默认映射为 `datetime(6)`。
> 如果建表用 `DATETIME(3)`，在 `ddl-auto=validate` 模式下启动时的结构校验可能失败 ——
> 这类问题只在启动时暴露。让建表精度与 ORM 默认值一致是零成本的风险消除。

**Q：为什么用物理删除而不是软删除？**

> 这个决策是被两个需求**组合**起来逼出来的：
> 删除后短码跳转要返回 404，且同一自定义短码要能被重新创建。
>
> 软删除方案在这里不可行。最直觉的做法是唯一索引改成 `(code, deleted_at)`，
> 未删除时 `deleted_at` 为 NULL —— 但 **MySQL 的唯一索引中 NULL 互不相等**，
> 所以可以存在多行 `(code='abc', deleted_at=NULL)`，
> 唯一性约束对未删除的记录**完全失效**。这会导致同一短码被创建多次，
> 是比"无法复用短码"严重得多的 bug。
>
> 可行的替代是加 `deleted_flag` 列，未删除为 0、删除时写为 id，
> 唯一索引建在 `(code, deleted_flag)`。但这样每个查询都必须加
> `deleted_flag = 0` 条件，**一旦有人漏写就会查到已删除的数据**，
> 这类 bug 在代码评审中很难发现。
>
> 我选择了物理删除。当前需求没有审计或回收站的要求，
> 为不存在的需求引入软删除，代价是让每条查询都多一个易漏的条件。
> 如果将来需要审计，正确做法是引入**独立的审计日志表**，
> 业务表保持物理删除。

### 2.6 关于部署与运维

**Q：怎么保证不会带着开发默认密钥上线？**

> 两层保护。
>
> 一，`application-prod.yml` 里的敏感项**没有默认值**，写成 `${VAR}` 而不是
> `${VAR:default}`。缺少环境变量时应用无法启动。
>
> 二，`StartupSafetyCheck` 在启动完成后检查配置，检测到仍在用开发默认密钥
> 就**拒绝启动**并打印具体是哪个变量。
>
> 为什么选择"拒绝启动"而不是"打警告"：带着公开可知的默认密钥运行，
> 比启动失败严重得多。启动失败会立刻被运维发现，而密钥泄露可能几个月都无人察觉。

**Q：健康检查为什么不用 TCP 端口探测？**

> 端口监听成功不代表应用可用 —— 可能仍在执行 Flyway 迁移，或数据库连接尚未建立。
> 用端口探测的话，编排系统会过早把流量导入，请求全部失败。
>
> 我用 Actuator 的 health 端点，它实际检查数据库和 Redis 的连通性。
> 另外我配置了 `show-details: when-authorized` 而不是 `always`，
> 匿名请求只看到 UP/DOWN，运维认证后才能看到是哪个组件不可用 ——
> `always` 会暴露数据库地址、磁盘路径等信息。

**Q：Docker 镜像为什么要多阶段构建？**

> 主要为了体积和安全。
> 完整 JDK + Maven 本地仓库约 700MB，只含 JRE 与 fat jar 的运行时镜像约 200MB。
> 体积直接影响部署时的拉取耗时。
>
> 安全上更重要的是：构建工具、编译器、源码不会进入生产镜像 ——
> 攻击者即使拿到镜像也无法从中获取源码或构建链的凭据。

**Q：日志里为什么要 traceId？**

> 没有它，排查线上问题只能在时间轴上靠时间戳猜测哪些日志属于同一个请求，
> 在并发环境下这种猜测基本不可靠。
>
> 我的 `TraceIdFilter` 为每个请求生成或透传 traceId 写入 MDC，
> 日志格式里带上它，响应头也返回给客户端 ——
> 用户报障时提供这个 ID 就能直接定位到具体请求的全部日志。
>
> 有个细节：我不直接信任客户端传来的 traceId。
> 因为它会被写入日志，原样接受任意字符串的话，
> 攻击者可以构造含换行符的值来伪造日志行（日志注入）。
> 所以我只接受符合预期格式（十六进制 + 短横线，8-64 位）的值，其余一律重新生成。

## 3. 可以主动暴露的不足

面试官问"这个项目还有什么可以改进的"时，**不要回答"我觉得已经比较完善了"**。
下面这些是本项目真实存在的限制，主动说出来并给出方案，比被追问出来要好得多。

| 不足 | 影响 | 解决方案 |
| --- | --- | --- |
| **没有真实上线运行** | 缺少生产环境的压测数据与故障处理经验 | 已完成部署编排，可在服务器上实际运行并压测 |
| **没有分布式锁** | 多实例部署时统计任务重复执行 | 引入 Redisson 或 ShedLock |
| **MySQL / Redis 单点** | 任一故障都会降级 | MySQL 主从 + Redis 哨兵 |
| **搜索无法用索引** | 单用户短链数超过数万时变慢 | 引入 FULLTEXT 索引或 Elasticsearch |
| **统计最多丢失 60 秒** | Redis 崩溃且未持久化时该时段数据缺失 | 已开启 AOF；更强保证需引入 MQ |
| **短码空间有限** | 568 亿条后回绕冲突 | 监控水位，接近 80% 时扩展到 7 位 |
| **没有接口级的权限模型** | 只有用户级隔离，没有管理员角色 | 需求规模未到，引入需重构权限模型 |

**推荐的表述方式**：

> 这个项目最大的不足是**没有真实上线运行过**。我完成了完整的部署编排，
> 但压测数据和线上故障处理经验只能从真实运行中获得，
> 而这两点恰好最能体现工程能力。
>
> 技术层面最需要补的是**多实例部署的分布式锁** ——
> 当前的统计刷库任务在多实例下会重复执行。
> 虽然 PV 的原子取出保证了不会重复计数，但仍是无效开销。
> 我在架构文档里把这一点明确记为已知风险，并给出了两个方案。

**为什么这样说是加分的**：它同时展示了三件事 ——
你清楚自己项目的边界、你区分了"能自己解决"和"需要真实环境"的问题、
你养成了把风险写下来的习惯。

## 4. 演示建议

如果面试允许现场演示，按这个顺序：

1. **`docker compose up -d` + 启动应用**（展示环境可一键复现）
2. **打开 Swagger UI**（展示接口文档与可调试性）
3. **演示跳转**：`curl -i` 短链，展示 302 与 Location 头
4. **演示统计**：连续访问几次后查统计，展示"数据是最新的"（尽管刷库有延迟）
5. **`./mvnw test`**（展示 77 个测试通过，重点提穷举测试）
6. **打开 `docs/adr/0002-short-code-generation.md`**（展示设计迭代过程）

**第 6 步是最有区分度的。** 大多数候选人只能展示代码能跑，
而能拿出一份记录着"我曾采用 A 方案，发现它有这个缺陷，因此改为 B 方案"的文档，
说明你具备设计评审的能力 —— 这是初级和中级工程师之间最明显的分水岭。

## 5. 一页速查卡

面试前 5 分钟过一遍：

| 问题 | 一句话答案 |
| --- | --- |
| 短码怎么保证不重复？ | Feistel 网络保证双射，无冲突是数学保证而非概率保证 |
| 短码怎么保证不可枚举？ | 密钥化 8 轮迭代 + Cycle-Walking，相邻输出无规律 |
| 跳转路径有多快？ | 命中缓存零数据库访问，统计只写 Redis |
| Redis 挂了怎么办？ | 降级直查数据库，因为 MySQL 是唯一真相来源 |
| 缓存穿透/雪崩？ | 空值缓存 TTL 60s / TTL ±10% 随机抖动 |
| 为什么不用 MQ？ | 需求只是 60 秒最终一致，Redis + 定时任务已满足，不引入额外组件 |
| UV 为什么用 HyperLogLog？ | 1 亿 UV 从 6.4GB 降到 12KB，误差 0.81% 对投放评估无影响 |
| PV 和 UV 为什么语义不同？ | HLL 无法做差集，UV 累加会重复计数，所以 UV 取 max |
| 怎么防越权？ | 归属校验作为 SQL 查询条件，不是查出来再判断；返回 404 而非 403 |
| 怎么防 XSS 跳转？ | 协议白名单（创建时）+ 跳转前二次校验（纵深防御） |
| 怎么防用户名枚举？ | 统一错误信息 + 占位哈希抹平响应时间差 |
| JWT 不可撤销怎么办？ | 双令牌：撤销放在刷新环节，损失窗口压到 30 分钟 |
| 怎么保证分层不被破坏？ | ArchUnit 架构测试，且它真的抓到了一个违规 |
| 为什么不用 H2 测试？ | 行为差异会产生"假绿"测试，比没有测试更危险 |
| 最大的不足？ | 没有真实上线运行；多实例缺分布式锁 |
